One request at a time

A bus lock serializes requests. Each new request toggles Q between 08 and 48. A pending transaction waits five seconds by default, then leaves a 50 ms command gap. Polling scans configured addresses sequentially.

Every decoded response stays observable

A separate queue holds up to 1,024 responses. Exact transmitted-request echoes remain visible for diagnosis, but do not update the model or establish communication. Queue overflow drops its oldest entry and logs the loss.

This package supplies the serial driver, CLI and offline simulator. It does not install a gateway service, publish MQTT telemetry, or connect to a cloud platform.

Escaping and recovery

On receive, 10 82 → 02, 10 83 → 03, and 10 90 → 10. Only an unescaped ETX terminates the frame. A new unescaped STX restarts it; a 1,024-byte limit bounds partial frames.

Transmit preserves the Java builder's literal bytes, including the command sequence 10 83. It does not add a general stuffing pass.

An additive sum, despite the name “CRC”

The original transmit calculation uses signed Java bytes; receive validation uses an unsigned sum. They agree for these empty polls. Receive checksum validation is optional and disabled by default; all five captured replies also pass when checked.

Application records, addresses and timestamps

Application responses are sliced from decoded offset 13. The first two application bytes are shared. The low nibble of byte 1 selects the process; the low nibble of each record's first byte selects its info type. Process 1 supports alarm/fault (info 1, stride 11), command reply (info 4, stride 8), and button indication (info 5, stride 10).

Records can be mixed and are applied in order. A partial known record rejects the response. An unknown type preserves the entire remaining application data because its length is not known.

The legacy request builder truncates the address to its low nibble. Configuration therefore accepts addresses 1–15 by default. Full-range addressing is an unverified opt-in. Timestamp decoding uses the Java epoch offset 631144800 + encoded_seconds; the physical panel clock and timezone are not established.

Command requests use a special 31-byte layout. The response table above is not a general command assembler or a vendor protocol specification.

FROM STARTUP TO RESTORATION

The panel lifecycle, through the driver.

The sequence below explains the integration's model. A real panel can enter an alarm directly, emit faults at any time, or use firmware-specific behavior. Only empty poll replies have been confirmed in the Pi's successful session.

ILLUSTRATIVE MODELNo device connection
01

Start and establish communication

Open the configured serial port, start receiving, then poll. online begins false; opening a port is not enough. A matching non-echo transaction marks it online. An empty reply changes no point or fault values.

02

Observe events

Events may arrive with a poll or unsolicited. The model has no discovery, initial snapshot, persistence or historical catch-up. Point keys (loop, device) must be configured in Python. A default local “normal” value is not a measured panel state.

03

Prealarm → fire alarm

Active occurrence 1 sets a configured point to prealarm; occurrence 2 sets alarm. Both loop and device must match, and detector type must be 6 or 7. There is one status slot per point: a later supported event overwrites it.

04

Acknowledge and silence

The driver has no separate operator-acknowledge command. A poll reply is a link response. Explicit silence() waits for a correlated command reply, accepting outcome 2; it does not clear the local alarm or track sounder state. Physical control effects remain unverified.

05

Restore and reset

An inactive supported point event sets its single status to normal. Accepted reset() clears local point and fault state. A received button indication with code 5 does the same regardless of its outcome field, following the reference. A later active event can immediately reassert the condition.

06

Track faults independently

Device-missing and general-device-fault events use the same point slot. Battery and supply faults have separate flags. A reset indication followed by battery-missing ends with that fault active—the ordering seen in the JACE application-log transcription.

07

Lose communication and recover

A poll timeout marks that panel offline without reopening the port. A receive failure marks all panels offline, fails a pending request, and attempts reconnect with a default backoff of 0.5–8 seconds. Point and fault values remain historical. Reopening does not reconstruct missed events; the next matched transaction re-establishes online status.

Power fault and communication loss are different observations.

A panel running on battery could report a supply fault if its firmware emits that event. A completely unpowered panel may instead time out. Zero receive bytes alone cannot distinguish loss of power from another communication fault. Neither power-event sequence was captured in the successful Pi session.

LOCAL SETUP

Start with the captured serial format.

Clone the private repository with an authorized GitHub account. Use Python 3.11 or later on a POSIX system. The velox.9600-odd.toml profile explicitly selects the settings used in the successful session.

TERMINALPassive / polling operations 
git clone git@github.com:NETIX-AI-OSS/velox-driver.git
cd velox-driver
uv sync --locked --group dev

# One poll per configured panel
uv run velox --config velox.9600-odd.toml -v poll

# Continuous polling and JSON responses
uv run velox --config velox.9600-odd.toml -v run

# Receive only; no transmissions
uv run velox --config velox.9600-odd.toml -v monitor

Configuration matters

Set the port to the actual RS232 UART. The captured setup used 8 data bits, odd parity and one stop bit, without software or hardware flow control. Keep a single process owner. The legacy library default is parity N; select O explicitly.

A TOML file overrides all serial/address CLI flags. The passive monitor command does not use the bus reconnect supervisor.

Understand the model before consuming it

Configure point keys through the Python API. No points are discovered by the CLI. Preserve raw records and track communication separately from event state. An offline panel can retain stale values, and a restart begins with fresh local state.

silence and reset are explicit commands with no automatic retries. This publication performed no live control operations.

Compatibility corrections and remaining ambiguities

The reconstruction deliberately corrects address parsing, exact loop-and-device matching, and mixed-record decoding. It adds strict decoded-length checks, bounded framing, response visibility, and echo rejection. These are intentional differences from the recovered code.

Polls match on address and exclude known transmitted echoes; they do not require the observed 28/68 flags or matching Q. Delayed same-address replies can therefore be ambiguous. Commands default to application number zero and correlate the original-command field; live confirmation is still needed. A matched command response sets online before its outcome is checked, so a rejected command does not imply offline status.

One point stores only one status, so an inactive event can clear a different active condition. Reset indications clear local state regardless of their outcome field. This event-fed model has no completeness/freshness marker for point state and no persistence or initial snapshot. It is not a validated life-safety monitoring system.
